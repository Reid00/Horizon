### [Rust 1.100 stabilizes never type and custom allocators](https://blog.rust-lang.org/2026/11/12/Rust-1.100.0/) ⭐️ 8.0/10

Rust 1.100 stabilizes the never type and custom allocators, and adds Cargo dependency cooldowns through a minimum publish age setting that makes the resolver ignore newer versions unless they are already in Cargo.lock. Cargo now warns about unused dependencies by default, and cargo install uses the lockfile already present in the .crate tarball by default, making --locked a no-op in that path. The release also includes lockfile behavior changes and additional stabilized APIs, according to the release notes and community reports.

hackernews · mbStavola · Nov 12, 18:39 · [Discussion](https://news.ycombinator.com/item?id=50472038)

**「Background」** Custom allocators in Rust have been developed through the allocator\_api effort: RFC 1398 set out the design for different allocator kinds, and the feature remained unstable while the standard library&\#x27;s allocation interfaces were worked out. Rust 1.100 stabilizes the core Allocator trait, allowing library authors to define custom allocators for use with Vec and Box on stable.

**「Cooldowns require opt-in」** Cargo&\#x27;s new minimum publish age setting defaults to zero, so upgrading to Rust 1.100 by itself does not change a project&\#x27;s supply-chain exposure; the cooldown only takes effect once it is configured per workspace, per machine, or system-wide. The RFC&\#x27;s reference configuration uses a 14-day minimum age, and versions already recorded in Cargo.lock continue to be kept on subsequent resolves.

**「Community discussion」** Commenters welcomed the long-awaited stabilizations and pointed out additional stabilized APIs not highlighted in the blog post, including bool::toggle, Box::map, str::trim\_prefix, str::trim\_suffix, and Path::trim\_prefix. One commenter asked whether compiler performance had improved and complained about large temporary files requiring frequent cargo clean.

**「Background」** CVE-2026-6460 is a PostgreSQL type-confusion vulnerability rated CVSS 8.8; vulnerability trackers state that an object creator can use ALTER ... SET DATA TYPE to execute arbitrary code as the operating-system user running the database. The research write-up describes the underlying primitive as 22 years old, presenting the exploit chain as work built on a long-present database-internals weakness rather than a newly introduced bug.

### [UMAP 0.6 adds faster initialization and opt-in optimizers](https://www.reddit.com/r/MachineLearning/comments/1xudaah/umap_06_new_initialization_new_optimizers_and/) ⭐️ 8.0/10

UMAP 0.6 is out with a new recursive initialization, new optimizers, and a nearest-neighbor search that maintainer Leland McInnes says is about 4x faster through better use of PyNNDescent. The release is installable via pip install -U umap-learn and conda-forge; McInnes reports that on 3 million arXiv papers it finishes in under five minutes, while a seeded UMAP 0.5 run takes 52 minutes single-threaded. The new initialization and optimizers are opt-in because they change the output, enabled with compatibility\_layout=False, and are intended to become defaults in future versions. McInnes also claims better fine-scale cluster detail and kNN recall at million scale, but these performance and quality claims are not independently verified here.

reddit · r/MachineLearning · /u/lmcinnes · Nov 12, 13:51

**「Background」** UMAP produces a low-dimensional layout by initializing points and then optimizing them against a nearest-neighbor graph, so both initialization and optimizer design strongly affect speed and quality. The 0.6 release changes both components and uses UMAP 0.5 as its baseline; the maintainer reports that a seeded 0.5 run on 3 million arXiv papers took 52 minutes single-threaded.

**「Impact」** Existing UMAP users will keep the previous layout behavior unless they set compatibility\_layout=False, so testing the speed and quality gains requires an explicit opt-in and may change downstream results; the release also makes seeded runs reproducible across all cores, according to the maintainer.

### [Solo audit finds no retinotopy or tonotopy in Meta&\#x27;s TRIBE v2](https://www.reddit.com/r/MachineLearning/comments/1xuillf/does_metas_brainresponse_model_tribe_v2_actually/) ⭐️ 7.0/10

A solo, self-funded researcher has posted a non-peer-reviewed audit of Meta&\#x27;s TRIBE v2 fMRI-prediction model, testing it with classic topographic-mapping stimuli—checkerboard wedges and rings, hemifield flicker, moving dots, and tone sweeps—and reports no retinotopic map \(d = 0.05, n.s.\) and no tonotopic map \(ρ = -0.07, n.s., even with loudness controlled\). The same audit reports sharp motion selectivity in MT+ \(d = 4.31, 52x enrichment over chance\). It also reports that an apparent eccentricity effect flipped to significant and &quot;correct&quot; under three separate stimulus-geometry controls, which the author interprets as an image-statistics confound rather than a positional code, and notes that TRIBE v2&\#x27;s methods spatially average video features before prediction. The author links code and a write-up; no independent replication is reported.

reddit · r/MachineLearning · /u/Own\_Tank1283 · Nov 12, 17:16

**「What TRIBE v2 is and what the audit tests」** TRIBE v2 is Meta FAIR&\#x27;s research model for predicting high-resolution fMRI responses from video, audio, and language inputs \[tool-2-1\]. The audit targets classic topographic maps—retinotopy and tonotopy, which encode visual-field position and sound frequency—and motion selectivity, a separate response property often localized to MT+; according to the source, the model&\#x27;s own paper did not test these maps.
